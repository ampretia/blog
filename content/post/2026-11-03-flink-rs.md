Interacting with a running Apache Flink cluster usually forces an awkward choice. Well, I think it's awkward at least. You can download the full Apache Flink distribution and use its built-in `bin/flink` tool. That works, but it requires a Java runtime on the machine, downloads hundreds of megabytes of dependencies, and expects local configuration files.

Alternatively, you can use the web dashboard. That is fine for casual debugging, but impossible to script and unnecessarily slow when all you want to know is whether three TaskManagers registered properly.

The remaining choice is hitting the JobManager REST API directly using `curl` and `jq`. The API is well-documented, but crafting multipart HTTP requests to upload JARs, polling for job completion, or parsing JSON status payloads in shell scripts quickly becomes tedious.

[flink-rs](https://github.com/ibm/flink-rs) fills that gap. It is a standalone command-line client written in Rust that talks directly to the [Flink REST API v1](https://nightlies.apache.org/flink/flink-docs-release-2.3/generated/rest_v1_dispatcher.yml) (targeting Flink 2.3). It compiles to a single static binary with no runtime dependencies.

This was also an experiment in writing a Rust CLI application, building a tool that was needed, and using a local neighbourhood coding agent to help.

## Why a dedicated REST client?

The Flink JobManager has exposed an HTTP REST API for a long time. In containerised environments such as Kubernetes or OpenShift, port 8081 is frequently exposed via a Service, Ingress, or Route.

However, the standard administrative experience has lagged behind the operational reality of running cloud-native clusters:

- **No JVM requirement:** A developer or deployment pipeline should not need a Java runtime installed just to check cluster health or cancel a runaway job.
- **Fast execution:** A native binary starts in milliseconds, making it practical in pre-flight checks, CI/CD runners, and shell aliases.
- **Static distribution:** Using `x86_64-unknown-linux-musl`, the resulting binary has zero shared-library dependencies and runs on virtually any Linux distribution or minimal container image (like `scratch` or `alpine`).

## Configuration

`flink-rs` can store the target cluster address in `~/.config/flink-cli/config.toml`, avoiding the need to pass connection parameters on every invocation:

```bash
flink-rs config set host http://localhost:8081
```

For transient environments or CI runners, the target can be overridden using the `FLINK_HOST` environment variable or the `--host` flag:

```bash
export FLINK_HOST="http://flink-jobmanager.production.svc:8081"
flink-rs cluster overview
```

## Inspecting cluster state

The `cluster` and `taskmanagers` subcommands provide immediate visibility into cluster resources:

```bash
flink-rs cluster overview
```

Output is rendered in a clear terminal table by default:

```text
Flink 2.3.0  commit a1b2c3

 Metric          │ Value
─────────────────┼───────
 Jobs Running    │ 2
 Jobs Finished   │ 14
 Jobs Cancelled  │ 0
 Jobs Failed     │ 1
 Task Managers   │ 3
 Slots Total     │ 12
 Slots Available │ 6

Status: HEALTHY ✓
```

To list registered TaskManagers and their assigned resources:

```bash
flink-rs taskmanagers list
```

## Managing jobs

The tool covers the standard job lifecycle: listing active and finished jobs, fetching job details, cancelling jobs, and retrieving execution results.

```bash
# List all known jobs
flink-rs jobs list

# Inspect detailed configuration and vertex status for a job
flink-rs jobs get 8d1f2a3b4c5e6f7a8b9c0d1e2f3a4b5c

# Cancel an execution
flink-rs jobs cancel 8d1f2a3b4c5e6f7a8b9c0d1e2f3a4b5c
```

### Live terminal watch

One common irritation when testing Flink jobs is wanting to watch state transitions without keeping a browser tab open or writing an ad-hoc shell polling loop.

`flink-rs` includes a `watch` command that continuously updates the terminal display until the job completes or the user exits:

```bash
flink-rs jobs watch 8d1f2a3b4c5e6f7a8b9c0d1e2f3a4b5c --interval 2
```

## Submitting JARs

Deploying application JARs to Flink via the REST API is a two-step process: upload the binary file to the JobManager's artifact storage, then submit an execution request referencing the resulting JAR ID.

`flink-rs` supports the explicit lifecycle steps:

```bash
# Upload a JAR file
flink-rs jars upload ./target/streaming-enrichment-1.0.jar

# Run the uploaded JAR
flink-rs jars run 7b3a9c1e-4f2a-4b1a-9a8c-123456789abc_streaming-enrichment-1.0.jar \
  --entry-class com.example.StreamingJob \
  --parallelism 4 \
  --args "--input kafka:9092 --output cos://bucket/data"
```

For everyday use and deployment automation, the `submit` command combines both actions into one:

```bash
flink-rs jars submit ./target/streaming-enrichment-1.0.jar \
  --entry-class com.example.StreamingJob \
  --parallelism 4
```

By default, `submit` uploads the JAR, initiates execution, and blocks until the job finishes or reaches steady state. For automated pipelines where asynchronous submission is needed, passing `--no-wait` prints the new Job ID and exits immediately.

## Automation with JSON output

Every command accepts `--output json`. This allows clean composition with tools like `jq` without fragile text parsing:

```bash
# Extract all running job IDs
flink-rs --output json jobs list | jq -r '.jobs[] | select(.state=="RUNNING") | .id'

# Assert available slots in a pipeline
AVAILABLE_SLOTS=$(flink-rs --output json cluster overview | jq '.["slots-available"]')
if [ "$AVAILABLE_SLOTS" -lt 2 ]; then
  echo "Insufficient cluster slots available: $AVAILABLE_SLOTS" >&2
  exit 1
fi
```

The output format can also be set permanently in the local configuration:

```bash
flink-rs config set output json
```

## Building and distributing

`flink-rs` is built with Cargo. Building standard debug and release binaries requires only a working Rust toolchain:

```bash
cargo build --release
```

For environments where glibc compatibility between the build machine and the target host cannot be guaranteed, building a static musl binary ensures complete portability:

```bash
# Install target and musl tooling (Fedora/RHEL)
rustup target add x86_64-unknown-linux-musl
sudo dnf install -y musl-gcc

# Build static binary
cargo build --release --target x86_64-unknown-linux-musl
```

The repository includes a `justfile` with recipe shortcuts for building Linux (x86-64 and ARM64), macOS, and Windows targets.
